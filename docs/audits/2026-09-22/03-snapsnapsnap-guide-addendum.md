## 3. Что новое свидетельство уточняет в аудите

### 3.1. Эти функции нельзя представлять как уникальность PicchuSpot

Сохранённые editing preferences, групповой выбор для Image Enhancement, markup, reference images и добавление Image Enhancement к другой услуге уже показаны в руководстве. Они остаются полезными требованиями к нашему workflow, но не являются самостоятельным конкурентным отличием. Основание: стр. 10, 13, 23, 26, 31, 34, 39–40.

Руководство подтверждает сочетание конкретных услуг; оно не доказывает, что у конкурента допустима любая комбинация всех услуг на одном фото. PicchuSpot также должен проверять допустимые сочетания по своему каталогу, а не принимать произвольные комбинации.

Кандидатное отличие PicchuSpot — лучшее исполнение процесса: меньше повторных действий, понятный итог инструкций, качественный результат и продолжение работы с тем же объектом. Преимущество по удобству/качеству ещё нужно измерить, а не объявить по PDF.

### 3.2. Камера — один слой, а не всё приложение

У руководства отдельный раздел съёмки (стр. 3–7), затем подробные настройки и submission flows четырёх услуг (стр. 8–43). Это усиливает приоритет коммерческого пути, уже предложенный в аудите: capture/import → выбор услуг → инструкции → review → существующий PicchuSpot backend → результат. Документ не доказывает спрос на наше приложение, но конкретизирует функциональный benchmark.

### 3.3. Необходимо разделить preferences и конкретные инструкции заказа

Источник показывает defaults в Settings и отдельные options при оформлении Staging. Но он не раскрывает правила наследования, синхронизации и изменения уже отправленного заказа. Ниже — наша рекомендация, а не описание скрытой реализации конкурента.

## 4. Предлагаемая продуктовая модель PicchuSpot

Сохраняется граница из AGENTS: local capture/import доступны до login; SQLite — единственная локальная metadata source of truth; auth, service catalog, pricing, uploads, orders и legal rules принадлежат существующему web/backend. Эта граница не изменяется конкурентным руководством.

### 4.1. Настройки съёмки отдельно от настроек обработки

Capture Settings относятся к устройству и способу получения исходников: mode, timer, aspect ratio, доступные объективы/zoom, grid/level, предупреждения. Никакого обещания 0.6x на неподтверждённом устройстве; параметры Balanced/Pro выбираются по нашим испытаниям.

Editing Preferences задают повторяемые предпочтения услуги: например, вид неба или стиль мебели. Они не запускают генерацию на телефоне и не являются новыми отдельными camera modes. Наличие переключателя в чужом интерфейсе не говорит, где и кем выполняется обработка.

### 4.2. Defaults → конкретный draft → зафиксированный заказ

Предлагаемый принцип: сохранённые предпочтения подставляются в новый draft; клиент может переопределить их для выбранных фотографий; в review виден итог; при отправке сохраняется точная версия инструкций. Последующее изменение Settings не меняет ранее отправленный заказ.

Нужно различать «не выбрано / наследовать», явное ON и явное OFF. Batch Apply не должен незаметно стирать индивидуальные overrides. Значимые художественные изменения должны быть видимы в review и согласованы клиентом. Это проектные требования, не вывод о юридическом соответствии.

### 4.3. Один Photo, несколько допустимых service assignments

Для пользовательского фото можно готовить несколько подтверждённых нашим каталогом услуг. Внутренние exposures Balanced не становятся отдельными оплачиваемыми фотографиями. Room type, style, notes, references и markup привязываются к правильному Photo и услуге, а не просто к последнему открытому экрану.

Это концептуальный контракт; имя таблицы, migration и API не выбираются здесь. Перед реализацией обязательно проверить текущие поля и совместимость в `MykhailoLy/real-estate-visual-studio`. Не создавать новую JSON-метабазу рядом с SQLite или дублирующий mobile backend.

### 4.4. Markup и references — инструкции, не перезапись оригинала

Минимальный markup: кисть/обводка, текст, undo, save и просмотр результата. Сохранить исходное фото без нанесённых линий; annotation/preview — отдельная инструкция. Привязку координат к ориентации/размеру кадра проверить отдельно. Reference images различать с изображениями объекта, чтобы они случайно не стали самостоятельными строками платного заказа.

### 4.5. Более короткий путь оформления

Основной предлагаемый UX:

`Shoot → выбрать фото → назначить услугу(и) → общие настройки + индивидуальные исключения → review → отправка`.

Единый reusable order flow с service-specific forms, а не четыре независимых мастера заказа. Для нескольких похожих помещений — «применить к выбранным», с ясным количеством снимков и возможностью индивидуального изменения. Это предложение PicchuSpot; руководство не раскрывает архитектуру компонентов конкурента.

## 6. Чего источник не устанавливает

Не раскрыты точный bracket count/EV spacing, shutter/ISO planner, алгоритм level и shake detection, HDR merge и место его исполнения, Camera2/AVFoundation implementation, Android device coverage, восстановление прерванной серии, offline consistency, upload retry/idempotency, токены/платёжный API, правила retention и детальный revision workflow.

В частности, before/after на стр. 29/43 — рекламные примеры, не основание объявлять in-app before/after slider. Руководство не описывает rework полностью; нельзя из этого заключать, что в приложении его точно нет. Вводная инструкция login на стр. 3 также не устанавливает обязательную авторизацию перед любой локальной съёмкой.

Источник не снимает технические риски A01–A10 исходного аудита и не закрывает cross-device acceptance Issue #18. Никакое изменение нашей Camera2 policy из этого PDF не следует.

## 7. Уточнение последовательности работ и стоимости

Сначала завершить ближайшие проверки надёжности/compatibility и спроектировать единый контракт заказа с учётом defaults и per-photo instructions. Затем довести один вертикальный коммерческий сценарий Quick/import + одна услуга до результата. Следующие формы добавлять поверх этого процесса, а не создавать четыре backend-пути.

Перед пилотом Virtual Staging должны появиться room type, style, notes, references и подходящий markup; они не должны оставаться абстрактными «когда-нибудь». Перед пилотом Item Removal нужен однозначный способ указать удаляемые элементы. Общие preferences и batch apply повышают приоритет для повторных заказов, но не требуют реализовать весь каталог одновременно.

Наличие этих форм не означает обязательных новых SDK-подписок или image-AI API. Дополнительный объём работ — модель данных и интерфейс preferences/overrides, сохранение/отправка reference и annotation assets, review, тесты и обработка заказов. Точный прирост часов/стоимости здесь не оценён: без проверки существующего web-контракта и утверждения формы заказа это было бы выдумкой. Условия сторонних компонентов также не исследовались в этом дополнении.

## 8. Acceptance checklist будущего заказа

Это рекомендации для следующих отдельных implementation tasks:

- Клиент исключает фото из заказа без удаления из Shoot.
- Поддерживаемые сочетания услуг и цены приходят из своего server-authoritative каталога.
- Видно, где используется default и где override; batch apply не уничтожает исключения скрыто.
- Изменение Settings после отправки не меняет уже отправленные инструкции.
- Notes/markup/references попадают к правильным Photo/service; originals остаются неизменными.
- Reference и annotation файлы не оплачиваются как новые фотографии объекта.
- Review показывает выбранные изображения, услуги, параметры, итог и заявленные сроки.
- Back/restart/offline не теряют draft; повтор submission не создаёт второй платёж/заказ.
- Переключение аккаунта не переносит приватные preferences/drafts другому клиенту.
- Capture mode, timer и доступные zoom presets не подменяют собой инструкцию по обработке.
